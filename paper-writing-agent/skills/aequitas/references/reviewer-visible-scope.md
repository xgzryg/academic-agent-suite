# 审稿人可见材料范围

本规则用于模拟同行评审，决定审稿意见可以依赖哪些研究材料。采用本规则先于正文解析、代码检查及其他审稿辅助流程。它不触发新的主角色选择。

## 先盘点，再确认

先复用本轮用户明确指定的范围；例如“只审这份 PDF”“手稿和附件都看，代码不看”“把这个仓库也纳入审稿”已经构成范围选择。简短复述后直接审，不为同一范围再次索取确认。

未指定时，只根据用户提交内容、文件名、目录清单和版本标识列出候选材料，不先读取整仓代码、内部笔记或所有项目文件。用当前宿主和模式允许的提问界面征求范围，优先使用支持选择及自由填写的软件提问功能。依工具规则处理必答问题；不能调用当前模式禁用的工具。没有适用界面时用一句自然语言询问范围并等待。范围未定期间可整理文件清单，暂不进行依赖范围的评审；预选项和沉默不代表用户选择。

供选择的三类范围，根据实际文件给出具体名称和版本：

- **投稿材料（推荐）**：本轮手稿、补充材料、主文及补充图表、图注；仅包含已提交或明确指定供审稿人阅读的版本。
- **投稿材料 + 代码**：上述材料及用户指定的代码仓库、脚本或 notebook；确认仓库版本或具体路径，避免默认整个工作区。
- **自定义范围**：用户指定文件或类别，可仅手稿，也可加入数据、分析输出、研究方案、注册资料或回复信。

单独列明尚未提供但被纳入范围的材料。原始数据、内部分析记录、历史版本、对话中的作者解释不因位于同一目录或已知其内容而自动纳入。多个候选版本无法判定时一并询问，不混用。公开文献可按任务及联网规则用于背景核查，引用时标明为外部来源；文稿链接的代码或数据仍须符合已确认范围，不能借文献检索扩展材料访问。

## 在可见范围内评审

- 全部虚拟审稿人和辅助流程沿用同一可见清单。确需不同审稿人查看不同材料时，由用户指定。向获准使用的顾问传递范围和必要摘录，避免整份作者侧上下文。访问代码的范围确认不另行授权安装依赖、运行代码或重跑分析。
- Calder 的方法学触发条件只有在代码已被明确纳入、且可读取时才成立。未纳入代码时，根据手稿评估方法描述及可复现性报告，不能声称检查了实现。
- 每条研究特定结论引用本轮可见材料的证据位置。可见材料没写清楚时表述为“未报告／无法据此判断／请澄清”，不能直接断言作者没有实施某步骤，也不能把未提供的代码判定为代码错误。
- 仅依据范围外资料发现的问题不混入审稿人结论。若用户还要求作者侧内部核查，单独标明其依据和身份；不得用内部知识替手稿补齐证据，也不得假称已经从既有对话中遗忘这些知识。
- 范围内某附件缺失或无法读取时，报告具体缺口并继续可评部分；仅当缺口阻止核心判断时才标该项无法评估。资料位于范围外本身不自动构成缺陷。

## 记录与延续

在审稿报告开头用一小段“审稿依据”写明实际阅读的材料及版本、是否包括代码/数据，以及会影响判断的缺失项。该段是用户要求的审稿依据说明，不受旧提示词禁止 preamble/coverage 等内部区块的规则排除；无需新增独立报告文件。

后续收到新材料时，只在用户明确将其纳入审稿后更新范围，并重评受影响意见。已确认的范围在同轮修订和顾问交接中复用，不重复启动访谈。
